# Режимы производительности

В интерфейсе доступны **Авто**, **Экономный** и **Максимальная скорость**. Настройки числа
одновременных фотографий пользователю не предоставляются. Глубина цвета
8/16 бит, пресеты и параметры проявки остаются независимыми.

## Реализация

- GUI работает в главном процессе, планировщик — в QThread, декодеры —
  в отдельных процессах с методом запуска `spawn`, включая Linux.
- Каждый процесс обрабатывает один снимок и освобождает память при выходе.
- Windows: «Авто» и «Экономный» используют BELOW_NORMAL_PRIORITY_CLASS,
  «Максимальная скорость» — NORMAL_PRIORITY_CLASS. Linux: соответственно nice
  не ниже 5 и не выше обычного унаследованного приоритета. Приоритет GUI не меняется.
- Потоки OpenMP / BLAS ограничены одним на процесс через переменные окружения
  до загрузки библиотек и через threadpoolctl после загрузки.
- «Экономный»: одна задача. «Авто»: первая задача используется для калибровки;
  после успешных файлов лимит растёт на один, до минимума из четырёх и
  количества доступных CPU минус один. Нижний предел — одна задача.
- «Максимальная скорость»: проверяет уровни 1, 2, 4… до числа доступных CPU,
  с тем же резервом RAM. Сравнивает число завершённых пикселей за секунду на
  каждой ступени (файлы из предыдущей ступени не участвуют). При приросте
  менее 5% возвращается к лучшей ступени и прекращает разгон до конца очереди.
  При нехватке памяти повышение параллелизма ограничивается бюджетом; после
  ошибки выделения памяти режим возвращается к одной задаче.
  Короткой очереди может не хватить для проверки всех ступеней. Измерения
  эвристические: меняющаяся сложность кадров и внешняя нагрузка влияют на выбор.
  В UI показывается только подсказка о других тяжёлых приложениях.
- Планировщик учитывает affinity и Linux cgroup v2. Заголовки RAW читаются
  в рабочем процессе без распаковки сенсора; сам декодер ждёт разрешения.
- Бюджет памяти — минимум 384 МиБ, либо 128 МиБ плюс 32 байта на пиксель
  полного сенсора. Коэффициент повышается, если реальные пики требуют запаса.
  Резерв системе — максимум из 1 ГиБ и 25% доступного общего лимита RAM.
  Учитывается и ожидаемый рост памяти уже запущенных задач.
- При временной нехватке RAM новые задачи ждут, текущие завершаются. При
  невозможности вместить снимок даже в общий бюджет отображается ошибка.
- Декодер пишет в отдельный временный каталог. После успешного завершения
  родитель публикует PNG через hard link без перезаписи; для FAT/exFAT и других
  файловых систем без hard links — через эксклюзивное копирование. Временный
  каталог удаляется после успеха, отмены или аварии декодера. Нативная авария
  декодера не оставляет частичный файл под окончательным именем PNG.
- Отмена кооперативная: вызов LibRaw нужно дождаться. Очередь не убивает
  процесс посреди записи. Остановка всей ОС/приложения не равнозначна нормальной отмене.

## Замер на пяти пользовательских Sony ARW

Все фотографии — 24 Мп; полный PNG RGB 16 бит, 4024×6024. Облачный Linux,
CPU quota 4 ядра. Измерена сумма RSS GUI и дочерних процессов с интервалом 25 мс;
она может повторно учитывать общие страницы библиотек. Замер не предсказывает
скорость Windows и не является жёстким лимитом RAM.

| Режим | Время пяти файлов | Пиковая сумма RSS |
| --- | --- | --- |
| Экономный | 51,79 с | 498 МиБ |
| Авто (финальная проверка, до двух задач) | 33,21 с | 764 МиБ |
| Диагностический фиксированный запуск двух задач | 32,16 с | 771 МиБ |
| Диагностический фиксированный запуск четырёх задач | 22,50 с | 1321 МиБ |

Фиксированные режимы использовались только внешним тестовым скриптом; их нет
в интерфейсе и настройках приложения. Диагностика четырёх процессов сознательно
не оставляла одно из четырёх доступных ядер свободным. Обычный «Авто» соблюдает
этот резерв. На пяти файлах плавный разгон достиг двух одновременно работающих задач.

Все пять PNG побайтово совпали во всех четырёх сравнительных запусках. В финальной
проверке PNG также побайтово совпали с исходными результатами Sony-проверки.
Максимальный интервал между тиками Qt-таймера в финальном замере — 71 мс
(со снятием скриншота); это проверка обработки событий
в offscreen Qt, а не тест отрисовки на реальном мониторе Windows.

Сравнительные замеры сделаны перед добавлением публикации PNG родительским процессом;
финальная строка «Авто» получена после её добавления. Публикация и очистка
дополнительно проверены отдельной очередью.
Исходные отчёты и сценарии находятся в `/workspace/artifacts/arw-validation/`:
`parallel-benchmark.json`, `final-auto-validation.json`, `parallel_benchmark.py`
и `process_smoke.py`.

### Проверка «Максимальной скорости»

Отдельно обработаны десять файлов (по две копии каждого из пяти пользовательских
ARW) в PNG 16 бит. Режим сам дошёл до четырёх одновременных задач на доступных
четырёх CPU. Очередь завершилась за 47,65 с, пиковая сумма RSS GUI и дочерних
процессов — 1308 МиБ. Все десять PNG побайтово совпали с предыдущими результатами.
В Linux проверен обычный приоритет рабочих процессов (nice 0), один внутренний
поток и работа Qt-таймера во время конвертации. Подсказка видима до запуска и во
время обработки. Это другая по размеру очередь, поэтому её время нельзя напрямую
сравнивать с таблицей на пяти файлах. Отчёт: `maximum-validation.json`, сценарий:
`maximum_validation.py` в той же папке артефактов.

## Проверки и ограничения

Тесты покрывают резерв памяти, рост параллелизма, CPU-лимиты, паузу/возобновление,
отмену, выход дочерних процессов, падение до и после чтения заголовка, отсутствие
перезаписи, очистку частичных данных, FAT fallback и связь настроек UI с движком.
С `RAW_TO_PNG_SAMPLE` выполняется настоящая конвертация в отдельном процессе и
отмена настоящего RAW. Windows-ветка приоритета проверяется с подменой системного
вызова; настоящий exe и оба реальных класса приоритета нужно проверить на Windows.

Модель RAM консервативна, но не заменяет системный hard limit. Другие программы
могут внезапно занять память; пониженный приоритет CPU не ограничивает память.
